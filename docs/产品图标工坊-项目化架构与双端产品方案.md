# 产品图标工坊：项目化架构与双端产品方案

状态：产品边界已确认，尚未授权实现。版本：1.0。日期：2026-09-08。

所属产品：产品图标工坊 / Make Product Icons。本文是下一阶段的单一产品与架构方案，不是 HETAO 图标设计需求，也不是当前 Skill 的生效指令。

本轮仅整理文档与文档索引；不改代码、运行数据、已安装 Skill，不部署网页。产品边界经本轮对话逐项收口；工具名称、格式示例与性能指标是据此制定的实现基线，不是当前已经可用的能力。当前完成度依据候选包源码核对，不把历史测试通过等同于新架构已实现。

## 1. 结论

产品不再定义为“生成图标的脚本加一个预览页”，而是一个 **由 Agent 驱动、WebMCP 优先、以本地文件为持久数据、由统一网页展示和审核的图标系统工作空间**。WebMCP 是高效入口，不是使用 Skill 的前提；没有 WebMCP 也必须能完成完整图标设计流程。

**先安装并加载 Skill，再选择在线或本地运行入口。** Skill 是两条路径共同的设计方法和操作规范，不仅是网页故障时才下载的备用包。在线运行不要求启动本地服务；本地运行才启动包内服务。

两种分发方式应是同一个产品的两个运行入口，而不是两套功能和数据格式：

- **Skill 版**：提供完整设计方法、启动与恢复规则、本地运行容器；优先通过 WebMCP 执行，不支持时通过 Skill 规定的本地操作流程完成同一业务。
- **网页版**：部署相同容器与工具合同，计算和项目文件读写在用户设备完成；网站服务器只分发程序、文档和不含用户数据的 Skill 安装包。
- **共同核心**：项目、需求、方案、图标、变体、任务、审核、历史、导出，以及一致的校验和状态协议。

现有“方案 → 图标列表 → 图标详情”可以保留为项目内部的主体。下一阶段主要补齐它上面的项目管理，以及它前后的需求确认、生产任务、维护恢复和工具覆盖，不应继续靠临时页面补功能。

最重要的四个架构决策：

1. 真正区分 **存储库 → 项目 → 方案 → 图标 → 变体**；存储库是位置和索引，不是又一个设计对象。
2. **先建立项目草稿，再确认需求，再允许生产**。建立项目不等于同意绘制。
3. **WebMCP 是优先业务入口，不是唯一入口，也不是文件权限、聊天模型或通用远程 MCP 服务器。** Skill 本地回退必须完整，不退化为只读查看。
4. **每一步都可结构化读取、修改、追踪、恢复，但不承诺每一步都能绕过用户授权而自动完成。** 操作系统目录授权等例外必须如实表示。

## 2. 已确认产品边界

| 事项 | 本文采用的边界 | 状态 |
| --- | --- | --- |
| 分发 | Skill 与直接部署的网页，两者共享产品核心 | 用户明确 |
| 开始使用 | 先安装并加载完整 Skill，再选择运行入口；优先在线，可主动选择或切换至本地 | 用户明确；不让 Agent 从零研究工具使用流程 |
| 数据 | 项目数据在用户本地，和容器、Skill 包分离 | 用户明确 |
| 数据接续 | 两个入口连接同一份已保存的项目，必要时重新授权；不复制、不转换数据 | 用户明确；只恢复已完整落盘的内容 |
| 历史数据 | 允许不兼容；旧项目只封存、不迁移，重新创建新版项目 | 用户明确；取消兼容层、转换器和迁移验收 |
| 版本提醒 | 增加检查 Skill 更新的 WebMCP 能力，发现新版提醒用户，不自动覆盖安装 | 检查对象由用户明确为 Skill；不含 CPU、浏览器或系统升级 |
| 层级 | 多项目，每个项目可以有多个方案 | 用户明确 |
| 入口 | 新设计工作先有项目，项目保存设计目的、目标和使用场景 | 用户明确 |
| 操作 | Agent 驱动，全部业务具备 WebMCP 能力；无 WebMCP 时由 Skill 标准本地流程完成，不建设独立业务 CLI 产品 | 用户明确 WebMCP 优先、不作为使用门槛 |
| 交互 | 聊天问答写入需求，网页实时反映状态 | 用户明确 |
| 人工编辑 | 需求在宿主聊天中补充，首版不提供手动填写的需求表单，不提供几何手动编辑 | 用户明确需求优先对话输入 |
| 必要人工入口 | 导航、查看、目录授权、安装包下载；安全停止/断开 | 既定查看功能、必要授权与安全控制，不提供手工设计表单 |
| 图标下载/方案导出按钮 | 提供工具，也允许用户直接点击下载/导出按钮 | 用户明确 |
| 浏览器兼容 | 支持 WebMCP 时优先使用；不支持时通过完整 Skill 本地方式完成设计 | 用户明确；撤销“无 WebMCP 就不能用 Skill”的限制 |
| 本地启动 | 内置本地服务，Skill 提供 Agent 可执行的标准启动、健康检查与恢复流程 | 用户明确；不要求用户操作命令行 |
| 并行 | 不限制多个 Agent/窗口编辑同一项目；不建议同时编辑，后一次成功保存生效 | 用户明确；不做项目锁、版本冲突拦截、自动合并或并发校正 |

以上产品决策已收口。后续实现不能重新引入 WebMCP 强制门槛、旧数据迁移、手动需求表单或独占写入限制；若需要改变这些边界，必须另行获得用户确认。

| 本地执行 | 前端调用 `/api/bootstrap`、`/api/command`，Python 校验、编译和落盘 | HTML 不是独立应用；直接上传静态托管不会获得这些能力 |

| 分发 | 候选 ZIP、已安装 Skill、历史静态页面并存 | 需单一构建源、版本清单、无真实数据检查和安装验证 |

### 3.1 当前命名存在的实质问题

当前 `projectKey` 实际是方案标识的兼容别名；当前几何 `projectId` 是一个方案绘制会话的身份；`workspaceId` 更接近未来的产品项目身份。直接再加一个 `projectId` 会让 Agent 不知道自己修改的是项目、方案还是几何工作区。

下一版重新定义合同，不能仅改页面标题。以下是新旧语义对照，不是旧数据转换映射：

| 当前字段/操作 | 当前真实含义 | 新合同 |
| --- | --- | --- |
| `workspaceId` | 一个集合及方案目录身份 | 新建项目独立生成 `projectId`，不建立旧 ID 映射 |
| `projectKey` | 方案的路由别名 | `schemeId` |
| 几何 `projectId` | 方案内写入身份 | `documentId` 或内部 writer identity，不冒充项目 |
| `get_project` | 读当前方案的完整几何数据 | 新版只读项目；几何放 `get_scheme` / `get_icon` |
| `save_project` | 编译当前方案 | `compile_scheme`，明确编译范围 |
| export `scope:project` | 导出当前方案 | 新版分别用 `scheme`、`project`、`library` 范围 |

使用明确版本的新合同，新版不注册旧工具、不提供旧参数兼容层或历史 URL 映射；一次会话只向 Agent 暴露一个完整版本，避免同名异义。旧容器与其数据可以一同封存，但不纳入新版生产流程。

## 4. 产品定位和非目标

### 4.1 面向谁

主要用户是通过 Agent 创建、扩展和维护产品图标系统的人。他们可能没有设计文件操作经验，但能通过聊天说明需求、判断图标是否合适。次要使用者是接手项目的另一个 Agent：它可能没有截图、DOM 或鼠标操作能力，必须仅凭工具恢复上下文并继续工作。

产品承担：需求与设计意图的结构化沉淀、图标语言的一致性、可控的几何生成、真实状态展示、可靠恢复、可维护交付。

产品不承担：自建聊天模型、默认云端保存业务数据、Figma 级手工绘图、自动获得目录权限、通用浏览器控制、任意磁盘访问、自动代码发布、图标商标独创性担保。

### 4.2 从源头文章继承什么

继承的是维护整套系统的方法：稳定的产品语义、按需要绘制尺寸/样式、重复结构一致、真实尺度审核、名称和标签搜索、源与交付物可追溯。不是照搬作者的品牌造型、字体交付、网站操作或发布命令。文章对元数据搜索、产品概念唯一对应及持续维护流程的说明，支持保留这些底层能力。[源文：The Making of Cursor’s Icons](https://www.minoradventures.co/blog/the-making-of-cursors-icons)

据此，大图标库的组织主轴应是“产品语义与图标”，而不是把每张图当作一份设计演示稿。场景是图标详情的检查手段，方案是相互隔离的设计方向。

## 5. 核心信息架构

```text
本地存储库 Library（授权的目录与可重建索引）
├── 项目 Project：产品背景、目标、需求、语义清单、任务
│   ├── 方案 Scheme A：本方案的视觉规则、实现与审核状态
│   │   ├── 图标 Icon：例如“应用身份”
│   │   │   ├── 变体 Variant：16 / Filled / Regular
│   │   │   └── 变体 Variant：64 / Filled / Regular
│   │   └── 图标 Icon：例如“菜单栏入口”
│   │       └── 变体 Variant：18 / Outline / Regular
│   └── 方案 Scheme B：同一项目的另一种视觉方向
└── 另一个项目：独立的目的、需求、方案与数据
```

### 5.1 对象责任

| 对象 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| Library | 已授权存储根、项目索引、最近打开 | 设计规则、跨项目共享默认几何 |
| Project | 产品目的、目标、用户、用途、约束、来源、需求版本和项目内语义清单 | 某方案路径的具体坐标 |
| Scheme | 一个完整设计方向、规则版本、图标实现、独立审核和历史 | 改写项目级事实、自动等同最终采用 |
| Icon | 一个产品用途或概念，稳定身份、名称、搜索标签、实现状态 | 以主图标/状态栏作为同一图标的尺寸选项 |
| Variant | 同用途下的光学尺寸、填充/描边、轻重等实现 | 新产品用途、应用预览的缩放倍率 |
| Task/Batch | 用户请求、计划、显式目标、执行与阻塞、产物 | 虚假的自动执行引擎或模型思考进度 |
| Review | 反馈与指定版本的接受/退回记录 | 编译成功或点击查看的同义词 |
| Delivery | 指定范围与版本的导出快照、哈希和来源 | 当前全部草稿、隐式上传或发布 |

### 5.2 多方案与多项目的规则

- 项目可有零个方案：刚创建、尚未确认需求是正常状态。
- 第一方案由已确认项目需求和明确视觉规则创建，不依赖一个虚构的来源方案。
- 一个项目可以一开始同时规划多个方案，也可以每轮增加一个。是否并行执行由宿主能力和明确请求决定。
- 方案默认一次只看一个，不混排；查看已有方案不等于选它作为最终方案。
- 项目可记录 `preferredSchemeId`，但必须是显式选择；切换浏览不改变它。
- 方案复制是独立分支，不是实时链接；组件变更不穿透到其他方案或项目。
- 单图标微调优先走版本历史，不自动复制整套方案。
- 切换项目清除活动选区、节点和“这里”的含义；写入永远使用显式 projectId + schemeId，不跟随当前焦点猜目标。

### 5.3 语义清单与方案实现

项目维护一个轻量的语义清单 `vocabulary.json`，保存稳定 `iconId`、名称、概念、tags 和已确认用途；每个方案引用它并维护自己的几何实现。

这不是新增第二套标签：`tags` 仍是唯一搜索同义词字段。不同方案对“搜索”可以有不同画法，但应能识别为同一产品用途。某方案尚未绘制该用途时显示待制作状态，不虚构 SVG。方案专属探索先记录为需求候选，确认用途后登记，不自动污染所有方案。

名称可改，ID 不随名称改动；相同名称在不同项目不构成同一对象。变体使用明确 `size`、`style`、`weight` 字段和独立稳定 ID，不通过字符串猜全部属性，也不要求沿用旧项目的 `16-filled` 键。新增轻重维度时不生成没有需求的笛卡尔积。

## 6. 从首次启动到持续维护的完整流程

### 6.1 首次启动

1. 用户打开在线网页或从已有 Skill 开始。网页提供“开始设计”引导及可交给 Agent 的标准指令；指令先指向固定发布来源的 Skill 安装与加载步骤，不直接让模型枚举全部 MCP、逆向网页或猜工作流。
2. 检查宿主是否已安装并加载对应 Skill。未安装时，在用户授权后由宿主/Agent 按标准方式完成安装；已安装则读取版本并复用，不反复安装。网页不能把点击下载、Agent 自述准备安装或持有 ZIP 当成已经安装成功，也不假定网页能直接读本机 Skill 目录。
3. 加载 Skill 后，Agent 按规范读取运行方式、工具目录和数据约定，只做当前容器的版本/能力核对与只读握手。安装和初始引导可以在项目目录连接前完成；安装不等于开始启动本地服务。
4. 选择运行入口：默认优先在线，可主动选择本地。在线具备所需 WebMCP 和目录能力时直接使用已部署容器，不启动 localhost 服务；用户选择本地或在线不可用时，由 Agent 启动 Skill 内置服务和容器。
5. 发现既有存储设置和当前目录项目标识；只读，不遍历用户整个文稿目录。没有设置时显示默认建议与更改入口，用户确认默认或自选目录，取得对应权限后才创建 Library。权限未授予不进入业务写入。
6. 新用户进入空项目库，Agent 根据聊天描述创建项目草稿；已有项目则读摘要、检查点和未完成任务。多候选且意图不明才问选哪个，不自动创建重名项目，也不要求用户手填长表单。

初始状态顺序为：需要安装/加载 Skill → Skill 就绪 → 选择运行入口 → 连接数据目录 → 工作就绪。每一步都能读取状态与失败原因；安装动作依赖宿主能力和用户授权，不承诺所有宿主都能由网页一键静默安装。

**“默认”是预填建议，不是静默授权。** 用户拒绝目录权限时，不写默认目录、不转存隐藏位置、不伪装已保存。

### 6.2 需求问答与实时填充

用户在宿主聊天框提供信息；Agent 先读当前 brief，提取事实，再调用工具更新草稿。网页显示整理后的信息及缺项，用户无需说“我填完了，你再读一下”。

例子：

```text
用户：做一个本地知识工具，给研究人员用，先做侧边栏和工具栏图标。
Agent → create_project / update_brief
网页：项目名、目的、目标用户和用途已呈现；未确认状态。
Agent：还缺首批语义与尺寸需求；结合已有材料只问必要问题。
用户：先做搜索、收藏、引用，按我们现有的 16px 描边系统。
Agent → update_brief / register_vocabulary_draft
网页：同步显示新内容。
Agent → prepare_confirmation（绑定这一版 brief 的摘要与哈希）
用户在聊天确认。
Agent → confirm_brief（引用确认回执与原 brief revision）
网页：需求已确认；下一步可建立方案和计划。
```

确认前只要求知道“做给谁、解决什么、为何需要这些图标、在哪里用、当前范围与约束”；参考、视觉气质等可以有清楚标注的建议，不为凑齐字段反复盘问。一般一轮最多三个影响决策的问题，不要求一次填完整。

更新 brief 的字段应包含来源类别（用户、已读取资料、Agent 建议）、来源引用和待确认标记。猜测不能写成已确认事实。首次项目名称未定可临时命名，不能阻塞草稿保存。

### 6.3 仓库资料路径

- Skill 本地运行时，用户提供路径后，可以通过受控资料工具只读发现 PRD、设计系统、已有图标与代表界面；禁止默认执行仓库代码、读取密钥和依赖产物。
- 网页版输入 `/Users/...` 只是文本，不授予访问权。需用户授权只读仓库目录，或让有文件能力的宿主提交已读取的资料摘要及来源。
- 资料目录与项目数据目录分别授权，项目目录写权限不延伸到资料目录。
- 外部资料默认保留原位；项目存引用、摘要、内容指纹和实际读取范围。默认不把完整源码打包进交付物。
- 网页工具没有网络或仓库读取条件时返回明确的能力缺口；用户可直接回答，不把仓库变成必选项。

### 6.4 方案与生产

需求确认 → 登记产品语义与首批范围 → 创建一个或多个方案 → 确认方案规则 → 生成明确的批次计划 → 逐个图标/变体绘制 → 校验 → 编译 → 审核。

所有步骤在同一容器内有工具，不要求停服改文件再重启。计划必须指明项目、方案、iconId、variantId、briefRevision、ruleRevision。新图标与新变体先登记，后绘制。校验门禁由核心引擎执行，不只靠 Skill 提醒。

批次默认不超过 20 个图标，可根据复杂度缩小。一个方案失败不阻塞其他独立方案。用户没有要求多方案时不强制生成三个方案，也不因图标多就自动调用多个 Agent。

### 6.5 审核、修改和交付

用户查看平铺列表，进入详情，切换结构、变体、场景，选择图层/节点，然后在聊天提出修改。Agent 读取活动上下文，定位目标，提交受控修改。不得用截图中推测的坐标替代已有结构化选区。

审核结论绑定具体版本：修订几何、共同组件或适用规则后，受影响的旧审核不能继续表示当前版本已通过。预览页继续不加自动评价、设计赞语和误读警告；正式反馈/审核状态属于任务记录，需查看时显示，不贴在每个场景下。

交付分开表达：草稿已保存、几何校验通过、SVG 已编译、用户已审核、已导出。五者不能互相替代。导出失败不回滚已经有效保存的图标；编译失败保留上一个完整生产版本与可恢复草稿。

### 6.6 再次调用与中断恢复

恢复顺序：用户明确的项目 → 当前目录项目标识 → 已授权 Library 的最近项目候选。目录相同不等于继续相同方案，最后访问也不等于用户授权继续写入。

Agent 读取恢复摘要：确认需求版本、各方案状态、未完成任务、最后成功检查点、待用户回答的问题、失败原因。不要重跑 intake 或已完成批次。

页面关闭、宿主断开、执行超时分别记录。能续跑的确定性本地操作按检查点恢复；需要模型续写的任务只标记“等待继续”，不能假装网页仍在生成。用户同时维护多个项目时，每个项目恢复状态独立。

## 7. 需求与任务的状态模型

不要用一个 `status` 字符串同时表示项目、需求、绘制、保存和审核。

| 对象 | 状态定义 | 转移依据 |
| --- | --- | --- |
| 项目 | active / archived | 创建、归档、恢复；不表示所有图标完成 |
| 需求版本 | draft / awaiting_confirmation / confirmed / superseded | 更新、请求确认、用户确认、新版本替代 |
| 方案 | draft / active / archived | 建立规则、开始维护、显式归档 |
| 任务 | planned / running / waiting_user / blocked / paused / succeeded / failed / cancelled | 工具受理、真实执行事件、确认、失败或取消 |
| 变体生产 | planned / draft / validated / compiled | 已登记、几何写入、对应版本校验、完整编译 |
| 变体审核 | unreviewed / changes_requested / accepted / stale | 用户结论及其绑定版本是否仍有效 |
| 持久化 | pending / persisted / failed | 实际磁盘写入结果，不由 Agent 文字设置 |

需求确认后若修改设计范围、用途、尺寸或约束，产生新草稿版本并计算受影响任务，不原地覆盖已确认版本。与变更无关的已有产物保留；只有受影响的任务或审核被标记待复核。

“正在思考”不能由容器自行计时推测。容器只呈现有依据的阶段、已完成对象数量、阻塞原因和最后事件时间。Agent 报告的阶段需标注其来源，不能抵充核心的校验或保存结果。

## 8. 网页结构：展示事实，不再堆操作入口

### 8.1 页面树

```text
项目库
└── 项目
    ├── 需求：当前确认稿、整理中的更新、尚缺信息
    ├── 方案区域：左侧方案列表，主区为当前方案图标库
    │   └── 图标详情
    │       ├── 图标结构：独立变体、画布、节点、真实尺寸
    │       └── 应用场景：固定预设，全部相关场景依序展开
    └── 任务与交付：当前批次、阻塞、审核记录、交付物
```

这是导航关系，不要求把所有层级同时变成侧栏。全局只显示项目身份和返回项目库入口；进入图标工作区后保留现有方案左栏；项目需求和任务按需查看。不能叠出项目栏、方案栏、图标栏三重侧栏。

项目库默认紧凑列出项目名称、设计目的、最近活动和待处理状态。不显示所有图标缩略图、不预加载所有项目。没有项目时说明可在聊天开始，不设必须手填的空白创建表单。

### 8.2 网页交互白名单

| 类别 | 人可直接使用 | Agent 工具 |
| --- | --- | --- |
| 查看 | 项目/方案切换、搜索/筛选、分页、详情、变体、结构/场景、网格/缩放、选中节点 | 全部必须有对应导航/状态设置工具 |
| 业务修改 | 默认无：不新建表单、不改需求输入框、不拖几何、不手动配场景 | 创建、补充、确认、绘制、恢复、归档等全部走业务工具 |
| 系统权限 | 目录选择、访问许可、必要安装下载；用户可拒绝 | 发起权限请求并读取 pending/granted/denied/cancelled，不能绕过 |
| 安全接管 | 保留停止/断开当前执行的入口，或由宿主提供可验证等效功能 | cancel_operation / revoke_session，同时记录真实状态；不占用项目、不踢掉其他会话 |
| 交付 | 保留直接 SVG 下载和明确范围的导出按钮 | 相同的受控读取/导出能力；不改变审核结论 |

首版不提供需求手动表单，用户在宿主聊天补充即可；导出明确保留工具与按钮双入口。两项都不再留作实现中的自由选择，系统权限和安全拒绝不会因采用 Agent 工作流而消失。

### 8.3 需求页不是表单

按“设计目的 / 目标 / 使用场景 / 首批范围 / 视觉约束 / 来源”分组展示当前结构化结果。缺失字段只在相关组标明，不显示成一整张待填问卷。用户在聊天补充后，同组内容立即更新；确认中的摘要固定到该版内容，不边改边确认。

不新增容器内聊天框。宿主聊天负责对话；容器负责显示整理结果。网页不读取宿主完整聊天历史，只知道 Agent 通过 WebMCP 或本地操作合同提交的信息，因此不能自动识别所有聊天内容或用户的情绪与注意力。

### 8.4 大图标库

- 一屏只属于当前方案，卡片是入口而不是永久选中对象。
- 默认每个语义图标一项，变体数作为摘要；详情再看变体。不把 600 个图标 × 多变体全部铺成长页。
- 如后续需要全库按尺寸/样式比较，可增加显示投影选择；它只选择展示方式，不创建变体、不改变原稿。这不是首版新的模式体系。
- 搜索匹配 name、concept、tags；标签不替代方案、不承担审核或任务状态。无有效标签时不放空筛选器。
- 数据端分页与缩略图按需生成，未打开项目不编译；前端分页、后端查询、预览缓存三者一起建设。
- 当前固定场景继续是用途预览、16/32/64/128 尺寸对比、反色预览；无已确认用途时不生成想象场景。缩放样本不能冒充新增光学原稿。

## 9. 本地存储与目录设计

### 9.1 首次默认位置

默认位置沿用 macOS 文稿下的 `Codex/Icon Projects/`；Windows 使用系统解析的 Documents 已知文件夹下 `Codex/Icon Projects/`。不要硬编码英文用户名或假设 Windows 文稿一定在 `%USERPROFILE%\Documents`，它可能被重定向。

首次显示默认位置，用户可接受或改为其他目录。支持“用当前调用目录”，但必须明确选择：若当前目录是代码仓库，默认在其中的 `icon-projects/` 子目录保存，不把配置和临时文件散落仓库根；若用户明确要求根目录本身作为项目，则尊重选择。

存储根可以更换；旧项目不自动搬迁或删除。配置记住已授权 roots，项目库能区分哪个位置当前可用。位置不可用时要求重新授权或重连，禁止悄悄在默认目录创建第二份同名项目。

### 9.2 可移植目录基线

```text
<用户选择的 Library 根>/
  library.json                         # 稳定 libraryId、格式版本
  projects-index.json                  # 可重建项目摘要索引，不存绝对设备路径
  projects/
    <projectId>/
      project.json                     # 名称、生命周期、当前 brief 引用
      design-brief.json                # 当前需求文档及确认状态
      vocabulary.json                  # 项目级语义、名称、tags、用途
      sources/index.json               # 授权资料引用、摘要、指纹
      requests/<requestId>.json        # 结构化用户请求，不复制整段聊天
      tasks/<taskId>.json              # 可恢复任务、批次引用与检查点
      schemes/index.json               # 方案目录
      schemes/<schemeId>/
        scheme.json                   # 方案身份、说明、规则版本
        design-rules.json             # 本方案几何规则的权威输入
        batches/<batchId>/generation-plan.json
        matrix/<iconId>.json           # 已编译版本的可编辑几何源
        primitives/<primitiveId>.json
        studio-state.json             # 持久草稿与撤销状态
        usage-bindings.json           # 只绑定用途与基准变体，不存页面布局
        icon-system.json              # 编译后的索引，不独立编辑
        build-manifest.json           # 几何、规则、SVG 的版本/哈希
        icons/<size>/<style>/<file>.svg
        reviews/index.json
      history/                        # 需求、规则及几何的版本记录/检查点
      operations/                     # 持久操作回执和执行结果
      exports/                        # 用户明确生成的交付物
```

这份目录仅用于新版新建项目，不移动或转换旧 HETAO 数据。稳定 ID 不使用显示名称，路径引用在项目内用相对路径；源资料可能在项目外，必须用独立授权引用。

本机配置只保存根目录选择、最近项目和恢复提示；放在系统应用配置目录，不能放进 Skill。网页版用浏览器存储记目录句柄和显示偏好；这些只是连接信息，不是业务数据的唯一副本。重新安装支持相同数据格式的 Skill 或更换浏览器后，重新选同一个 Library 就能按 manifest 找回项目。不支持的格式只报告不兼容，不自动转换。

### 9.3 权威数据和派生数据

权威输入：确认需求、语义清单、方案规则、登记计划、持久几何草稿/源、组件定义、审核记录。

派生结果：SVG、图标索引、缩略图、数量摘要、场景预览、搜索索引。派生数据损坏可重建，不得反向覆盖权威输入。

草稿和生产源必须显式区分：编辑成功即保存草稿；编译才推进 production revision。读取接口说明取的是 draft、compiled 还是具体 revision。UI 显示的 SVG 引用其实际来源版本，不混用旧 SVG 和新坐标。

### 9.4 持久化、失败与并发

- 每个写入有 requestId 和明确目标；版本/哈希用于显示来源、缓存失效与查询历史，不作为多人写入的拒绝条件，不要求 `expectedRevision`。
- 同一运行会话在回执有效期内重试同一 requestId，返回已有结果，不重复执行。回执不存在或已过期时明确返回结果未知，先读现状再决定是否重发；不建设跨进程全局去重或恰好一次协议。
- 变更先做格式和几何校验，再保存。基本的非法路径、无权限、目标不存在和写盘失败仍需报告；多个 Agent 存在、读到旧版或别的会话尚未退出本身不是拒绝条件。
- 单文件采用完整内容写入及底层可用的安全替换机制，避免正常保存时主动留下半段 JSON；多文件/大批次逐项返回成功与失败，不增加跨文件事务管理器，也不承诺跨端原子提交。
- 中途断电、关闭容器或写盘失败后，读取磁盘中最后可验证的完整源/草稿，损坏的派生预览可重建。无法解析的数据不继续写坏、不删除未知文件；这一基本失败处理不是并发冲突校正。
- **同一项目允许多个 Agent、多个窗口以及在线/本地同时打开和编辑，不设置占用、项目锁、租约、抢占或第二会话只读限制。** 在 Skill 规范与属性说明中提示一次“不建议多个 Agent 同时编辑同一项目，后保存的内容可能覆盖此前修改”，不检测到多人就弹窗或阻止保存。
- **覆盖规则：同一个被保存的文档/文件，以最后一次成功写入完成后的内容为准。** “后”按实际落盘先后，不按用户开始聊天的时间或不同设备的时钟排序。操作保存整个文档时，旧副本可能覆盖其中前一个 Agent 的修改；不做字段级合并、不比较基础版本、不进行冲突裁决。未被该操作写入的其他文件不因这次保存而主动回滚。
- 不为并行写入承诺全局顺序、跨文件一致快照或完整多方审计历史。底层文件 API 自身拒绝或失败时如实报告，允许用户重试；不把系统失败伪装为成功，也不额外实现调度或锁来保障并发。需要可靠的连续修改时，使用规范建议用户顺序操作，但不是使用门槛。
- 一个原语组件变更仍需列出受影响图标并执行正常校验；版本历史和回执在常规单路径使用中继续有效，不承担多人合并功能。
- 新版兼容格式内的归档默认可恢复；首版不提供永久删除整库的工具。显式恢复写入当前目标时同样按后保存生效，不覆盖目标范围外的未知同名文件。历史不兼容数据的封存不等于可在新版恢复编辑。

### 9.5 在线与本地接续（已确认）

- 两种入口用相同格式读写同一个用户目录，以 libraryId / projectId 识别同一项目；无需导入、导出或复制项目来切换。这是新版入口接续，不是第 13 节已取消的旧格式迁移。
- 目录授权和路径记录不是跨入口共享的凭据。能从已授权配置定位就复用；无法定位时让用户重新选择原目录，读取项目标识核对，不遍历整个磁盘、不在默认位置新建替身项目。
- 正常切换建议先完成保存，再由另一入口读取原目录最新有效数据；不要求旧会话释放、交接令牌或独占接管。用户可以保留两个入口，同时写入按后保存生效。
- 在线容器异常、失去目录权限或浏览器退出时，本地端从最后一个完整落盘的检查点恢复；仍在原网页内存中的未保存内容不承诺可找回。原目录权限未能取得时如实等待，不显示虚假的已恢复。
- Skill 与在线容器需要支持同一数据格式；工具版本不匹配可引导检查 Skill 更新。不兼容时拒绝写入并说明，不暗中转换旧数据或把“切换”做成迁移工程。

## 10. 双端运行架构

```text
用户 ↔ Agent 宿主的聊天
          ├── 优先：网页原生 WebMCP
          └── 回退：Skill 标准本地操作入口 → 内置本地服务
                         │
                         ▼
统一操作合同 / 参数校验 / 权限与确认门禁
          ▼
共享业务核心（项目、需求、任务、审核、几何、编译）
  ├── 状态同步 ↔ 统一 HTML 容器（展示、预览、导航与选区）
  └── 持久化 → 存储适配层
                 ├── Skill：内部本地服务 → 用户已授权目录
                 └── Web：浏览器目录句柄 → 用户已授权目录
```

### 10.1 技术路线基线

目标是共享业务合同、数据格式和同一套确定性几何/编译核心；不长期维护“本地 Python 一套、浏览器 JavaScript 另一套且结果各不相同”。

把不依赖文件系统的核心整理为可在浏览器 Worker 与本地运行时使用的 TypeScript/JavaScript 模块。前端不必因此换框架；现有结构和样式可以保留。文件读写和系统目录解析走适配器，不设计跨端写入锁。

当前 Python 引擎可作为几何算法的只读参考；使用合成测试验证共享核心，不要求旧项目能载入、旧数据能转换或旧接口可调用。Skill 阶段完成共享核心和跨平台存储适配后，再将网页版作为部署与浏览器存储阶段。技术重构不等于旧数据迁移，不为历史数据增加比对或转换工程，也不在校验失败时偷偷切换引擎。

是否通过 WASM 复用算法，留给技术验证；将整个 Python 运行时塞进网页虽是备选，但包体、启动和依赖成本需证据，不作为当前默认答案。

### 10.2 Skill 版

包含：Skill 方法、机器可读流程合同、共享容器构建产物、共享核心、存储适配、内部启动器、完整本地回退操作规范、诊断能力、许可证与版本清单；不包含旧数据迁移器或旧协议兼容层。

内置本地服务已确认。Skill 给出 Agent 可执行的标准启动流程：检查已有会话与运行时 → 复用或启动 → 校验健康与版本 → 取得实际 URL 和会话身份 → 选择 WebMCP 或本地回退。用户不需要操作命令行；不因端口占用随意终止别的服务。

不建设一套面向用户的业务 CLI，也不新增本地 MCP 服务器。Agent 可以通过其已有的执行/文件能力按 Skill 规范调用内部本地入口；这与要求浏览器或宿主支持 WebMCP 是不同的能力前提。具体回退设计见第 10.6 节。

本地服务仅监听回环地址，动态可用端口，明确本次会话标识和打开项目。启动前说明并获授权；运行期间复用会话。服务健康、连接失效、重连和预期存续时间有明确状态。不要让一次工具执行结束就顺手关闭用户仍在审核的服务，也不要建立未经授权的永久后台守护进程。

运行时版本作为支持矩阵的一部分：能复用受支持运行时则使用；缺失时说明要求或引导下载匹配运行包，不静默安装全局依赖。第一版需验证 macOS 和 Windows；现有 POSIX 项目锁不带入新版，也不另建跨平台项目锁。

本地包携带运行所需的 HTML、脚本、样式与几何资源，完成安装和环境准备后，容器展示、本地计算及文件读写不依赖 CDN 或在线业务服务；更新检查联网失败不影响它们。Agent 使用的模型是否需要网络由宿主决定，不把容器可离线运行宣传为所有在线模型都能离线。

### 10.3 网页版

HTTPS 站点交付静态资源，项目处理在浏览器内；不把现有 Python API 放公网访问用户目录，也不要求在线页面跨来源调用 localhost 服务。网页的 Worker 负责重计算，文件适配负责落盘。

网页必须附带完整 Skill 下载与标准开始指令，安装并加载 Skill 是两条路径共同的起点，不仅是故障降级提示。安装由用户授权、宿主/Agent 执行；Skill 就绪后可继续在线，完全不启动本地服务。安装包采用与站点对应的构建版本和校验值；不把用户正在看的项目塞入包。工程上“统一 HTML 框架”是单一应用壳和路由合同，不要求把所有程序、依赖和数据合并进一个巨大的 HTML 文件。

无账号、无云同步、无模型 API key 输入，是首版默认范围。网站不保存项目内容；Agent 宿主可能把工具返回的资料交给其模型服务，这与网站是否上传是两件事，隐私说明不能承诺“数据绝不离开设备”。

### 10.4 能力检测与完整回退

WebMCP 当前是仍在演进的浏览器能力：网站注册工具，宿主需要实际发现和调用；不能从“浏览器名叫 Chrome”推断完整可用。用能力探测、一次只读握手和真实回执判断。浏览上下文及来源权限限制同样适用。[Chrome WebMCP 概览](https://developer.chrome.com/docs/ai/webmcp)

| 检测结果 | 产品行为 |
| --- | --- |
| 尚未安装或加载 Skill | 首先完成标准安装/加载引导；只开放引导和必要环境检查，不进入图标业务流程 |
| WebMCP + 兼容 Agent + 目录读写可用 | 网页完整工作流 |
| WebMCP 可用，但宿主尚未调用 | 如实显示尚未建立连接；本地 Skill 可采用标准回退，不阻塞已有工作 |
| WebMCP 可用，目录 API 不可用 | 引导 Skill 本地版，不降级为隐藏浏览器存储后声称等价 |
| Skill 就绪，但在线页面无可用 WebMCP | 使用已经安装的 Skill，转到本地运行；不要求用户重新安装、填表或手工绘图 |
| 本地 Skill 无可用 WebMCP | Agent 按标准本地流程完成需求、绘制、审核、修改、导出与恢复；HTML 容器继续展示 |
| 用户拒绝目录权限 | 保持未连接，不创建或丢弃业务数据 |

不再使用“你的 Agent 不支持 WebMCP，所以不能使用本 Skill”的判断。只有两条执行路径都缺少实际宿主能力时才准确报告缺项，例如既不能调用 WebMCP，也不能启动或访问本地运行环境；不能把所有失败归因于浏览器。纯聊天、无任何本地或工具权限的宿主不是可执行 Agent，但用户无需为了获得 WebMCP 而被强制更换一个已有本地执行能力的 Agent。

在连接信息中可给一次轻量提示：“使用支持 WebMCP 的浏览器和 Agent，可更直接地同步上下文、提高操作效率。”提示是优化建议，不是错误状态、不反复弹出、不遮挡当前设计。回退状态明确显示真实入口，不伪装 WebMCP 已连接。

### 10.5 网页本地目录的真实限制

目录选择需要浏览器许可和用户交互，不能只凭 Agent 传来一个路径就得到权限；`startIn: documents` 只能建议对话框起点，不是静默写入文稿的许可。[MDN：showDirectoryPicker](https://developer.mozilla.org/en-US/docs/Web/API/Window/showDirectoryPicker)、[File System Access 目录规范](https://wicg.github.io/file-system-access/)

授权后的句柄可用于重复访问，但启动时必须复查许可；清理站点数据、换浏览器或换站点来源都可能需要重新连接。以磁盘内 libraryId / projectId 恢复，不依赖浏览器记住绝对路径；某些环境只提供目录名和句柄，就如实显示“所选目录”，不编造完整路径。

不把 OPFS 作为正式项目的唯一存储：它按来源隔离、不是用户可直接管理的文稿目录，清除站点数据会删除其中数据；可用于缓存或临时计算，不能替代用户选定目录。[MDN：OPFS](https://developer.mozilla.org/en-US/docs/Web/API/File_System_API/Origin_private_file_system)

### 10.6 无 WebMCP 的 Skill 标准本地流程

**完整回退能力是用户已确认要求；本节采用共享操作合同的内部接口作为实现方案，不恢复旧协议，也不以迁移旧数据为前提。**

1. Agent 按 Skill 的启动规范运行内置本地服务，读取本次会话的地址、版本、受控访问凭据和操作能力清单。凭据仅在本次授权范围传递，不写入公开 URL 或打包产物。
2. 本地服务提供与 WebMCP 同源的内部操作分发接口。Agent 用宿主已有的 HTTP 请求能力，或执行 Skill 提供的最小调用示例，提交相同的 operation、参数和目标身份；不需要安装 MCP 桥或学习另一套业务命令。
3. 全部业务能力由同一核心受理，创建项目、需求确认、登记计划、几何修改、编译、场景读取、反馈、导出、更新检查和恢复均不能仅在 WebMCP 包装层实现。回退同样能发现操作 schema、读真实状态和查询失败原因。
4. Agent 可读取规范化本地源文件作为上下文，生成几何候选后通过同一校验和保存入口落盘；不自行伪造事件日志或审核状态。不把裸写 JSON 当成绕过权限和几何校验的正式流程，但不因另一个 Agent 保存了新版本而拒绝当前合法提交。
5. HTML 容器订阅或拉取本地服务状态，提交成功后立即反映最新内容；网页导航和选区也同步回本地会话，Agent 能读取选中了哪个图层/节点，而非要求用户口头重述。容器关闭或上下文过期时明确报告，不拿上一次选区假充当前选区。
6. 回退允许比 WebMCP 多几次调用或显式状态查询，但功能、数据格式、确认规则和最终产物保持一致，不推出能力缩水版。两个入口使用同一请求格式与后保存生效规则；切换时先读磁盘与可用回执，不盲目重放已完成操作，不要求跨端全局幂等或写入者协调。

Skill 需提供一条从空目录到完整图标交付的本地操作示例，以及接手已有新版项目的恢复示例。它们是标准使用规范，不是要求 Agent 自己逆向网页、猜字段或编造 API。

纯在线页面在无 WebMCP 时，回退是使用开始阶段已安装的 Skill 打开本地容器，不是让公网网页越权访问本机文件。两种发行物仍共享同一核心、容器和当前格式，重新连接原目录继续已保存工作。

## 11. WebMCP 全流程工具合同

### 11.1 完整的定义

不是暴露任意读文件、执行 JS 或通用 `set_state`。完整意味着：每个产品对象都有必要的发现、读取和生命周期操作；每个流程阶段都有状态、门禁、失败恢复；每个人工查看行为都能结构化观察和导航。

工具清单、输入 schema、返回 schema、限制和错误码来自同一份定义。Skill 的流程说明引用该合同；不能维护“文档里有工具，运行时没有”的第二份名单。

下表既是 WebMCP 完整覆盖要求，也是 Skill 本地入口的操作能力清单。共享同一参数与结果定义，由入口适配调用同一核心；WebMCP 优先不意味着只能从 WebMCP 读取状态或执行业务。

以下使用 `icon_studio_v3_` 前缀，表中省略。名称是目标合同基线，不是当前可调用工具；实现可调整命名，但不能减少能力或改变已确认边界。

### 11.2 工具覆盖目录

| 能力域 | 必需工具 | 关键内容 |
| --- | --- | --- |
| 发现 | `get_capabilities`, `get_workflow` | 引导阶段可读：Skill 安装来源/加载状态及证据、所需版本、运行入口、目录连接状态、分步门禁和 schema；不能只返回工具名称或伪造安装完成 |
| 会话 | `get_session`, `get_view_context`, `get_selection` | 绑定项目、当前页、显式目标、节点/手柄、未展示缓存、焦点、UI状态 |
| 导航 | `navigate`, `set_view_options`, `select_geometry` | 项目/方案/详情、搜索筛选/分页、网格缩放、图层节点；只改视图 |
| 存储 | `get_storage`, `request_storage_access`, `get_permission_request`, `disconnect_storage`, `scan_projects` | 默认建议、授权范围、许可状态、受控索引恢复；只扫描授权范围 |
| 项目 | `list_projects`, `get_project`, `create_project`, `update_project`, `open_project`, `archive_project`, `restore_project` | 零方案项目、名称/目的摘要、归档、独立上下文；创建不自动导航 |
| 需求 | `get_brief`, `update_brief`, `validate_brief`, `prepare_confirmation`, `confirm_brief` | 草稿字段、来源、缺项、确切版本确认、变更影响 |

| 规则 | `get_design_rules`, `propose_design_rules`, `confirm_design_rules`, `get_impact` | 规则版本、受影响组件/图标/批次；不能自动改全库 |
| 变体 | `list_variants`, `register_variants`, `retire_variant`, `restore_variant` | 明确 size/style/weight、用途及注册任务、退役引用检查 |

| 任务 | `list_tasks`, `get_task`, `report_task_progress`, `pause_task`, `resume_task`, `cancel_task` | 真实操作与产物关联、等待用户/失败/续跑；报告不能伪造成功 |

| 组件与几何 | `list_primitives`, `get_primitive`, `apply_operations` | 当前路径、曲线、分组、布尔、组件定义等受控操作；严格嵌套 schema |
| 验证/编译 | `validate_icon`, `validate_scheme`, `compile_scheme` | 几何/注册/规则/来源检查，逐对象结果与构建版本 |

| 审核 | `record_feedback`, `list_feedback`, `resolve_feedback`, `record_review`, `get_review_status` | 用户原意、具体目标、版本；接受与校验通过分离 |

| 交付 | `prepare_export`, `get_export`, `read_artifact` | 项目/方案/图标/变体明确范围，源包/SVG 包区别，字节或文件引用 |
| 操作状态 | `get_operation`, `list_events`, `wait_for_events`, `cancel_operation`, `get_recovery` | requestId 去重、游标、真实写盘结果、取消与恢复 |
| Skill 更新 | `check_skill_updates`, `get_skill_update_status` | 非业务能力：查询 Skill 发布版本，返回当前/最新版本、检查与提醒状态、发布说明及下载地址；不修改项目，不自动安装；规则见第 12.4 节 |

这不是要求无区别地把几十个工具全部塞进每次模型上下文。可按阶段分组发现，但 `get_capabilities` 必须能找到所有合法能力及缺失原因。原型验证后可合并完全同构的读取接口；禁止为了少几个工具而退化成任意文件写入或模糊的万能参数。

### 11.3 统一请求与返回

写入请求必须包含明确目标和请求唯一 ID，不带用来阻止覆盖的基础版本门槛。可带 `sourceRevision` 记录来源，但不做比较交换校验；返回 revision 是内容版本标识，不是跨端全局序号。普通写入不需要总是传 UI contextId；用户说“这个图标”的指代式修改仍绑定该会话的当前上下文，避免写到另一个图标。这是目标识别，不是同项目多人写入限制。

```json
{
  "projectId": "p-001",
  "schemeId": "s-001",
  "iconId": "i-001",
  "variantId": "v-016-outline",
  "sourceRevision": "content-a12",
  "expectedContextId": "session-7:42",
  "requestId": "req-unique",
  "taskId": "task-003",
  "operations": [{"op":"move_node","layerId":"shell","nodeId":"n2","handle":"point","point":[8,3]}]
}
```

```json
{
  "ok": true,
  "status": "completed",
  "operationId": "op-003",
  "target": {"projectId":"p-001","schemeId":"s-001","iconId":"i-001","variantId":"v-016-outline"},
  "revision": "content-b13",
  "persistence": "persisted",
  "eventCursor": "event-104",
  "data": {},
  "warnings": [],
  "nextActions": ["preview_icon", "validate_icon"]
}
```

异步操作先返回 `accepted` 和 operationId，不返回假成功。权限返回 `waiting_user` 与 permissionRequestId。失败给稳定 code、用户可读原因、是否可重试及恢复操作，不只传一段异常字符串。

最低错误集合：`CAPABILITY_UNAVAILABLE`、`PERMISSION_REQUIRED`、`PERMISSION_DENIED`、`TARGET_NOT_FOUND`、`CONTEXT_CHANGED`、`BRIEF_UNCONFIRMED`、`TASK_UNREGISTERED`、`VALIDATION_FAILED`、`STORAGE_UNAVAILABLE`、`SAVE_FAILED`、`RECEIPT_EXPIRED`、`SCHEMA_UNSUPPORTED`、`CANCELLED`。不定义因多人写入或旧基础版本而拒绝的 `WRITER_CONFLICT`、`STALE_REVISION`、`EXTERNAL_CHANGE` 门禁。

### 11.4 选区、会话和跨项目保护

- 当前选区是完整 projectId / schemeId / iconId / variantId / layerId / nodeId / handle；每个层级允许合理的 null，不默认选第一个。
- 图标列表无活动几何选区；应用场景只选图标，具体样本另带源变体；结构视图才有变体与节点。
- 用户切页、切项目、切节点时 contextId 改变。需把检查与指代式写入放进同一受控受理步骤，不能只在几秒前读过一次选区就认为安全。
- 后台明确目标的任务可以继续原项目，不因用户去看别的项目而换目标；也不能抢走用户当前浏览页。
- Agent 接入会话有绑定目标、权限和内容版本信息；每个会话有自己的视图上下文，不设置业务写入锁，其他会话打开同项目不使本会话失去编辑资格。
- 任意 Agent 的注释、资料内容、图标名称都属于数据，不得成为执行任意代码或提升权限的指令。

### 11.5 实时反馈与 Agent 唤醒

业务核心在本次运行会话内产生有序事件，UI 和该入口的工具读取同一事件源。每个事件含目标、操作、阶段、版本和时间；不是把 DOM 文本抓回来拼成状态。不建设跨独立进程的全局事件排序；另一入口的保存可通过刷新磁盘状态反映，查询状态时说明数据来源和读取时间，不用本窗口缓存冒充所有会话的最新结果。

`list_events(afterCursor)` 补读，`wait_for_events(afterCursor, timeout)` 支持有界等待和取消；游标过期返回需重新快照的信号。宿主支持订阅时可做通知适配；不支持时 Agent 用工具等待/轮询。

WebMCP 的工具目录变更事件不等于我们的业务事件，也不保证网页能主动唤醒所有宿主里的空闲 Agent。方案必须以工具回读可完成为底线，通知作为宿主能力。不能承诺“用户做任何事，所有 Agent 都会立刻知道”。[Chrome Imperative API](https://developer.chrome.com/docs/ai/webmcp/imperative-api)

### 11.6 确认与权限不能伪造

需求确认要求绑定内容哈希、revision、确认摘要与来源记录。宿主如果支持可信确认回执则优先使用；只有 Agent 自述用户同意的环境，记录为宿主转述，不能当作可验证的人类签名。关键破坏性操作不能仅凭模型填写 `confirmed:true` 放行。

确认绑定的是用户实际看过的那一份内容，不能把确认 A 版说成确认 B 版；这与允许多人后保存覆盖并不冲突。不用需求确认记录或哈希比较实现通用保存门禁，也不因另一个 Agent 在线而禁止更新需求草稿。

业务规则必须在核心强制执行；WebMCP 的只读/重要操作注解有助于宿主判断，但不是权限认证。初始目录许可、外部来源读取和高风险恢复都需对应的有效授权范围。[Chrome WebMCP 安全说明](https://developer.chrome.com/docs/ai/webmcp/secure-tools)

## 12. 保持工具产品的可维护性

### 12.1 两条完整操作路径的验收

两套独立验收必须走完：列项目 → 新建草稿 → 问答写 brief → 确认 → 首方案 → 登记图标/变体/批次 → 几何 → 编译 → 读取场景 → 记录反馈 → 修改 → 导出 → 中断恢复，并验证 Skill 更新检查。

- WebMCP 路径：使用只能调用 WebMCP、不能截图/读取 DOM/点击页面/执行 shell 的测试宿主；不能偷偷靠本地回退补缺失工具。
- Skill 回退路径：禁用 WebMCP，使用具有标准本地执行与文件/HTTP 能力的 Agent，只按打包 Skill 的规范完成全流程；不能临时启用 WebMCP、要求手工填需求表或逆向容器来补步骤。
- 两条路径都验证页面更新、当前选区读取、同目标后保存生效和入口切换读取现有结果。相同合成输入得到相同几何、校验与导出结果；效率差异不变成功能差异。多窗口顺序保存时第二次不得因其他会话存在或来源较旧而被产品拦截。

需要用户确认的系统目录权限仍由用户做；本地服务遵守宿主已授予的文件权限。测试必须验证 Agent 能读到等待与完成结果。不能用自动点击偷偷补几步后宣布任一路径完整。

### 12.2 稳定性与规模目标

首版规模验收基准：一个 Library 20 个项目；一个项目 5 个方案；一个方案 600 个图标、每图标最多 4 个已登记变体。是测试规模，不是产品硬性限制。现有 3 方案 × 2 图标只能用于功能冒烟。

分页默认 48，工具单页最多 100；不得生成全库 SVG 再分页。缩略图按 source/rule/renderer revision 缓存；节点/复杂布尔预览在 Worker 或后台计算，避免阻塞导航。

性能目标基线：已建立索引的搜索/分页本地 p95 ≤ 300ms，缓存详情切换 ≤ 200ms，长操作 1 秒内返回可追踪 operationId。明确硬件、浏览器、冷/热缓存后测量；未测不宣称达标。正常使用下的持久化和可恢复性优先于这些性能目标；不把多人覆盖导致的修改丢失算作需要并发校正的新范围。

### 12.3 隐私和攻击面

项目内容、文件路径、日志、工具输出默认不发送网站后台；遥测默认关闭或严格剔除业务数据。静态资源请求仍会到站点，不能称“无网络活动”。用户所选目录如果被 iCloud/OneDrive 等同步，工具不能保证操作系统不会同步。

不将 session token、目录句柄、密钥写入 URL、导出包和公开错误。项目资源只允许已注册文件，资料读取默认最小必要、分页和长度限制；不开放通用磁盘路径工具。本期不提供项目 ZIP 导入或旧数据转换入口；外部资料仅按已授权的只读来源处理，不执行其中脚本或 HTML。

第一版不支持任意 SVG 导入转可编辑矩阵，也不迁移旧的本工具项目。第三方图标集只能作为已授权的只读参考；需要制作时在新版重新登记和绘制，不能假装所有 SVG 都可无损还原成我们支持的结构。

### 12.4 Skill 更新检查与提醒

**范围已确认：检查这个 Skill 是否有新版本。** 属于非业务性的维护能力，不检查 CPU、操作系统或浏览器更新，不是项目数据版本升级器。以下为该能力的实现与验收规则。

- **检查来源**：读取产品固定官方发布源的稳定版清单，包含 skillId、Skill 版本、发布日期、发布说明、包下载地址、校验值、工具合同及数据格式支持范围。站点和 Skill 包都携带可识别版本；未配置发布源应明确报告，不虚构最新版本。不接受 Agent 任意指定更新服务地址，不执行发布说明中的内容。
- **工具**：`check_skill_updates` 发起或复用一次检查，`get_skill_update_status` 读取缓存结果、不触发网络；WebMCP 和 Skill 本地入口均可调用。返回 `checking / up_to_date / update_available / unknown / check_failed`、当前版本及其来源、最新版本、checkedAt、缓存是否过期、下载信息和不兼容说明；首次联网失败、未知当前版本都不能返回“已经是最新版”。
- **自动触发**：每次 Skill 启动或会话恢复时检查；24 小时内有成功结果则复用，活跃会话超过该间隔在下一次操作时重查。Agent 可显式请求立即检查。检查异步执行，不阻塞创建项目、保存和审核；不为更新检查单独运行常驻进程，不承诺网页或宿主关闭后仍能通知。
- **提醒方式**：发现新版本后，网页给一次非阻塞更新提示，同时写入会话事件，Agent 可经工具读取并在聊天提醒。相同目标版本去重，用户收起后不在每次操作中重复弹出；更新状态仍可查询。没有新版本时不常驻显示“已是最新版”，离线或失败只记录可查询状态，不打断业务。
- **网页版的边界**：网页可查询最新 Skill 下载包，但不能仅凭浏览器访问就知道本机安装的 Skill 版本。只有实际 Skill 会话提供版本时才做“已安装版本落后”的判断；宿主转述版本要标明来源。当前版本未知时返回 `unknown` 与可下载的最新版本，不声称已经检测到本机需要升级。
- **安全和数据**：检查只读取发布信息，不上传项目内容、目录、用户标识或业务日志；发布源会收到普通网络请求。下载或安装需另行明确动作，检查工具不替换包、不重启容器、不热更新正在运行的任务。不兼容时提醒“旧项目不转换，需重新创建”，不附带迁移步骤或迁移工具。

验收覆盖：旧版发现新版、当前已最新、当前版本未知、离线、超时、发布清单无效、缓存过期、同版本重复提醒抑制、显式重查，以及不兼容提示。用合成发布清单验证，不依赖真实发版才能测试。

## 13. 历史数据：只封存，不迁移（已确认）

用户明确接受新架构与旧数据不兼容，后续在新版重新创建项目。不为旧数据增加工程量。

- 不开发迁移器、旧 ID 映射、旧接口/路由兼容层、旧需求合并或历史格式转换；不安排 HETAO 迁移演练。
- 现有项目和对应旧容器可原样留存为封存资料，不覆盖、不清理、不导入新版；本轮文档更新不实际移动文件或停止旧预览。
- 新版扫描仅识别受支持的格式。不兼容目录被识别为不可打开，不自动重建、升级、重编译或覆盖；新项目写入独立的新目录。
- 封存不建设专门的档案产品：保留原文件即可，不承诺旧容器永远可运行，也不要求新版能预览旧工程。
- 新版支持格式内的崩溃恢复、历史撤销、数据持久化仍是必要能力；它们和旧格式迁移是两回事，不能一并取消。
- 后续发布若发生数据格式不兼容，必须在更新提示中说明“旧项目不转换，需重新创建”，不能用“可更新”暗示旧数据一定可继续编辑。

## 14. 分两阶段落地

### 阶段一：Skill 版建立完整本地闭环

| 子阶段 | 交付 | 完成门槛 |
| --- | --- | --- |
| A0 合同落地 | 层级/目录/状态/工具schema/人工入口/版本提醒规则 | 按第 16 节已确认决策落地；不以 UI 改造代替合同，不增加迁移或并发协调工作 |
| A1 共享核心与存储 | 提取确定性核心；本地适配、基本文件保存、根目录配置 | 合成几何测试、Windows/macOS 新建读取恢复；无第二生产编译器或项目锁 |
| A2 项目与需求 | 项目库、草稿项目、问答落盘、来源、确认、第一方案 | 从空目录分别用 WebMCP 和 Skill 本地路径到达已登记生产任务，无独立业务 CLI 产品 |
| A3 维护链 | 批次/变体新增、任务事件、审核、历史、归档、导出、恢复 | 新增图标不再停服；中断不会重跑完成任务；指代式写入不串项目 |
| A4 单一容器与打包 | 新页面树、只读展示、权限例外、Skill 更新检查、完整本地操作规范、无数据包 | WebMCP/无 WebMCP 两条端到端、新版本提醒、大库和失败用例通过；旧数据不被写入 |

阶段一内置本地服务，WebMCP 优先，标准本地入口保证无 WebMCP 的完整流程；使用宿主 shell 发起内部调用不等于建设独立业务 CLI，也不能借此绕过共享核心。保留当前页面成熟部分，不同时重做字体、颜色和图标设计。候选通过后再单独获得安装/替换授权，不能把完成文档当成全局安装许可。

### 阶段二：网页版直接部署

| 子阶段 | 交付 | 完成门槛 |
| --- | --- | --- |
| B1 浏览器存储 | 目录授权、句柄恢复、完整文件保存与读取恢复 | 无本地服务也能保存重开；拒绝/撤权/清缓存场景诚实可靠；不限制写入会话数量 |
| B2 Web 运行 | 浏览器 Worker 核心、部署入口、宿主握手、事件读取 | 与 Skill 共用合同和几何结果；不访问网站业务数据 API |
| B3 分发与兼容 | 首次安装/加载 Skill 引导、版本检查与提醒、版本/哈希、能力探测、非阻塞效率建议 | 新用户先加载 Skill，再直接在线使用且不启动本地服务；需要时切换本地完整流程，包内无用户数据 |
| B4 互通与发布 | 同格式本地/Web接续、离线资源与程序回滚 | 顺序使用同格式项目时接续已有数据；并行覆盖按既定规则，不兼容时拒绝写入、不做转换，缓存不混版本 |

网页上线不是“把当前 assets 上传服务器”。共享核心、浏览器本地存储和完整工具闭环是上线前置。阶段二不另造项目格式，不加入账户、云端数据和 MCP 服务器来绕过限制。

### 不进入这两阶段的内容

云协作与账号、多人实时协同合并/写入锁/冲突裁决、通用本地 MCP 桥、手工矢量编辑器、字体生产流水线、任意 SVG 无损导入、旧数据迁移与兼容层、项目 ZIP 导入、公开作品社区、自动提交/推送仓库、复杂多工作区管理、未经许可的常驻服务。多窗口本身不禁止，只是不建设协同保障。后续如需增加，另行评估，不混进本次“补完整”。

## 16. 产品决策定稿

本轮产品待决问题为零，以下是后续实现必须遵守的边界：

1. 先安装并加载完整 Skill，再选择在线或本地入口；Skill 给 Agent 标准工作流，不让模型从零研究 MCP。
2. 在线直接运行已部署容器，不启动本地服务；本地由 Agent 按 Skill 规范启动包内服务和容器。WebMCP 优先，不支持时也能走完整本地流程。
3. 数据存在用户本地、与包和容器分离；首次确认存储位置，默认系统文稿下 `Codex/Icon Projects`，可更改。两入口读取同一目录已保存的数据，权限可重授，不因切换复制或转换项目。
4. 需求在聊天中输入，首版不提供手动需求表单和几何编辑；下载 SVG 与导出同时提供工具和手动按钮。
5. 不限制多个 Agent/窗口编辑同一项目，只说明不建议同时编辑；同一目标后成功保存的内容生效。允许覆盖，不做锁、占用、基础版本拦截、自动合并或并发校正。
6. 提供检查 Skill 更新的 WebMCP 能力及同等本地入口，自动检查和提醒，不自动安装或覆盖当前包。
7. 旧数据原样封存、不迁移，允许新旧格式不兼容，不建设转换器与兼容层。
8. 保持轻量 HTML 容器与本地运行能力，不增加云端账号、数据服务或协同平台。已安装本地包的展示、计算和文件操作应能离线运行，联网更新检查失败不阻塞；模型本身的联网要求、在线站点首次加载和文件授权仍取决于实际环境。

工具命名、内部模块、文件布局示例和性能目标是以上边界下的工程基线，不要求用户逐个批准技术细节；调整它们不得改变产品范围、增加平台化能力或重开已经明确排除的工作。正常需求流程中记录用户尚未回答的信息，不属于本产品方案存在未决项。

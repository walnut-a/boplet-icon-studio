# 图标设计方法原点对照审查

日期：2026-09-15。范围：当前仓库 Skill、合同、业务核心和展示代码的只读审查。只新增本文，不修改实现、安装版或真实图标项目；没有重新运行测试或开展真实图标库视觉验收。工作区既有开发计划、视频及研究文档改动不属于本次审查。

## 结论

方向符合，不能称为严格完整或完美遵循。当前方案已经形成可靠的图标生产与管理基础，但尚未形成同等完整的图标设计质量体系。流程的严格程度高于视觉质量检查的严格程度。

原文是具体项目经验，不是通用合规标准。应继承系统思维、视觉判断与持续维护方式；不应将 Cursor 的风格参数、字体交付与旧库替换路径强制推广至所有项目。

来源：[The Making of Cursor’s Icons](https://www.minoradventures.co/blog/the-making-of-cursors-icons)。本文对原文的核心提炼是：以产品语义组织整套图标，通过独立尺寸设计、光学校正、横向比较和可维护交付保持统一；工具与规则不能替代视觉判断。下文是对本仓库的独立判断。

## 已有实际基础

| --- | --- | --- |

| 探索与反馈 | 独立方案、矩阵历史、用户原文反馈、主方案选择 | 支持保留备选和继续细化；历史记录不等于便于比较的探索总览 |
| 可追溯交付 | 编译内容哈希、源快照、导出合同及交接流程 | 是图标交付基础；Skill 软件包发布不能等同用户图标库进入其产品的发布管线 |

## 主要缺口

### 1. 规则能保存，但多数设计判断还依赖 Agent 记忆

`src/contracts/models.js:44` 附近的规则合同包含 gridSize、padding、strokeWidth、cornerRadius、lineCap、lineJoin 和 opticalNotes。缺少独立的尺寸规则表、光学轮廓分类、重复修饰符约定与例外记录。文本说明可以承载判断，但工具不能据此可靠找出哪些图标偏离同一套约定。

`src/core/geometry.js` 从图层取实际描边宽度和形状半径；规则中的 strokeWidth、cornerRadius 不是全面强制执行的几何约束。允许局部例外是必要的，问题在于目前不能明确区分有意修正与无意漂移。

### 2. 几何有效不等于设计合格

`src/core/production.js:37` 的 validateGeometry 调用几何引擎并检查墨迹边界；`src/contracts/production-operations.js:91` 的 validate_icon 返回 valid、bounds、contentHash。它没有检查视觉中心、局部拥挤、元素间隙、视觉重量或跨图标协调性。

当前方法文档已经提醒“几何通过不等于用户认可”，这是正确边界。后续不应通过增加主观分数或逐图标审批来填补缺口，而应让 Agent 在扩库、修改共享规则及交付前完成有具体比较对象的设计检查。

### 3. 缺少按重复构造组织的横向检查

当前 query_icons 按 name、concept、tags 检索，组件工具可以列出并读取源几何。尚未发现按共同组件、修饰符、轮廓类型或尺寸规则组织的跨图标审查入口。

例如，能搜索“文件夹”，不等于能集中比较所有使用同一加号修饰符的图标。能创建组件，也不能证明之后的新增图标复用了该组件或使用了有依据的例外。此处是最值得优先补齐的系统能力。

### 4. 固定预览与真实产品验证仍有距离

`src/contracts/maintenance-operations.js:29` 的 get_context_preview 从绑定用途和源变体生成样本，按距离选择接近展示尺寸的源稿；固定尺寸对比为 16、32、64、128。`src/app/app.js` 的 sceneBoard 用占位条表现邻接内容。

该预览有助于检查尺寸和反色，但不包含目标产品真实字体、文字重量、控件密度、交互状态和运行设备。当前 Skill 尚未把这些因素形成明确、可重复的检查步骤。不能据此断言现有图标不好，只能确认当前证据不足以证明已达到该层面的质量要求。

### 5. 小规模品牌探索尚不能证明大图标库设计能力

README 和官网案例以 Boplet 品牌图标为主，适合说明探索及反馈。开发计划中的规模测试证明的是数据与界面承载能力，不能证明大量不同语义图标具有共同视觉语言。

下一次设计验证宜采用一个真实产品的代表性 UI 图标组，包含曲线、斜线、宽窄轮廓、重复对象、修饰符及密集细节，再增加一批新图标验证能否延续规则。建议起步约 12–20 枚；这是本次建议，不是原文规定或已确认范围。

## 建议顺序

1. 先细化设计方法：代表性样本、独立尺寸判断、局部光学校正、规则例外及真实产品检查；保持对话与当前界面结构，不新增用户手填表单。
2. 用一个真实 UI 图标组走完探索、细化和扩库，记录实际发现的漂移及修正依据。
3. 依据真实问题补最小工具支持，优先考虑重复组件引用查询、同类图标比较和规则变更影响检查。不要先增加庞大规则引擎或主观评分体系。

这些是审查建议，没有自动转为已确认需求，也没有改动唯一开发进度账本。无需为了对齐原文恢复旧数据迁移、强制字体导出、增加 Figma 依赖或自动推送。

## FileBox 试点实测补充（2026-09-15）

本节为后续实际测试，替代开头“没有开展真实图标库验收”在本节范围内的状态。使用原 FileBox 项目、A 安静的工作台方案，本机 dev.4 / build `cf325371`，不替换 FileBox 应用图标，不修改原方案几何。

### 已取得的证据

- 当前 HTML 会话的 Skill 阶段为 `design_ready`；通过 WebMCP 读取单项合同，再执行真实项目验证与导出。
- 16 枚图标各有 16、18px 两份源稿。`validate_scheme` 最终 32 项全部成功；`prepare_export` 最终 ready，32 份 SVG 均经 `read_artifact` 校验读取，并打包保存到本机验收目录。
- 16px 描边为 1.25，18px 为 1.35，源几何分别保存，非整份等比缩放描边。导出原稿制成 16/18px × 浅/深背景的横向验收板，配系统字体 13px 检查；这仍是独立对照板，不代表 FileBox 原生控件内验收。
- 方案登记了六个组件，文件夹、中转确实引用对应尺寸组件，16px 下载及排序共享向下箭头；18px 排序引用对应箭头组件。
- 合成数据上的七项生产、维护、组件拆分、恢复和导出测试通过，覆盖修改后旧审核失效、交付必须来自最新编译、非法几何保留源、暂停任务拒绝写入与组件拆分不改变墨迹。该证据不冒充真实 FileBox 方案已完成修改验收。

### 发现与判断

1. **实际尺寸检查入口不足。** 文件夹场景回执包含 16/24px 导航、16/32/64/128px 对比及 64px 反色；24px 及以上来自 18px 源稿放大，缺少 18px 原尺寸直接对比。这次用外部验收板补证，但日常 Skill 流程仍容易跳过目标尺寸。
2. **共享构造存在未说明的例外。** 18px 下载使用独立箭头路径，18px 排序使用 `prim-arrow-down-18`；16px 两者都使用共享组件。不能仅据此判定设计错误，但应比对几何差异并记录是否为有意的光学例外，不能把“定义过组件”视为扩库一致性完成。
3. **视觉候选问题，尚非用户结论。** 原尺寸浅深底检查未见明显裁切；“更多”相较文字与其他图标显得偏轻，预览眼镜形态的语义需要真实产品上下文验证。不能将这轮观察写成用户已接受或直接据此覆盖源稿。

下一轮优先围绕上述具体问题完成小批次细化与真实 FileBox 场景验证，再用新增图标检验规则延续性。当前可判定生产、验证、导出链路通过；还不能判定设计体系已完整遵循原文精神。
